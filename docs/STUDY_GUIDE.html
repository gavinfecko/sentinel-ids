01 The pitch

What it is, in one breath

sentinel-ids passively watches a network interface, decodes every packet, and decides whether the traffic is an attack. It does this two ways at once: stateful heuristics that recognize behavior over time (a port scan is many connection attempts in a few seconds), and a signature engine that matches known-malicious byte patterns in payloads (a SQL injection string, a Log4Shell probe). Every alert is tagged with its MITRE ATT&CK technique, streamed to a live console, logged as JSON for a SIEM, and rolled into an HTML report.

The project has two halves that meet in the middle. The defensive half is the IDS. The offensive half is a Kali Linux VM that runs real attacks so each detection is proven against genuine traffic, not a simulation. A separate engagement roots a deliberately vulnerable Metasploitable target and the IDS watches that too.

The one-sentence version for a recruiter
"I built a Python IDS that detects scans, floods, spoofing, and web exploits in real time, mapped every detection to MITRE ATT&CK, and validated it end to end by attacking my own lab with Kali and rooting a Metasploitable box."
02 Architecture

How a packet becomes an alert

The pipeline is deliberately simple and single-purpose at each stage. Understanding this flow is the fastest way to answer "walk me through your code."

03 How detection works

Stateful heuristics

Signatures alone can't catch a port scan, because no single packet is malicious. The trick is state over a sliding time window. Each heuristic keeps a small per-source history and fires when a threshold is crossed. Two shared mechanisms keep this practical:

  • Sliding windows track events per key (usually source IP) over a rolling number of seconds, so "15 distinct ports in 10 seconds" is a natural rule.
  • Cooldowns collapse a flood into one alert. A 500-packet SYN flood should page you once, not five hundred times.
  • Garbage collection drops idle keys every 30 seconds so memory stays bounded on a busy link.

04 Signature engine

Matching known-bad payloads

The signature engine loads 20 rules from rules/signatures.yaml, each a compiled regex with a protocol, a port set, a severity, a description, and a MITRE technique. It runs them against packet payloads. Rules cover web exploits (SQLi, XSS, directory traversal, command injection, Log4Shell, Shellshock), scanner fingerprints (sqlmap, Nikto, Hydra user-agents), reverse shells, cleartext credentials, and the specific Metasploitable exploits this project used.

The evasion story worth telling
The first live run missed a SQL injection. The attack URL-encoded its spaces as %20, and the regex expected literal whitespace (union\s+select). That is a classic IDS-evasion gap. The fix hardened the pattern to also match %20, +, and /**/ comment evasion, then re-attacked to confirm the catch. "I found an evasion in my own tool and closed it" is a strong thing to say out loud.

05 The lab & networking

Where the packets actually flow

The lab is two VirtualBox VMs and the macOS host, all on hardware you own. The networking choices are the part interviewers probe, because they reveal whether you understand what you built.

Detection lab: Kali attacks the host

Kali is bridged onto the same LAN as the Mac, so the Mac's sensor sees Kali's packets directly. Bridged networking over Wi-Fi has a known quirk: the access point expects one MAC per client, so host-to-VM unicast is flaky, but VM-to-host works cleanly, and that is the only direction the IDS needs.

Pen-test lab: Kali attacks Metasploitable

Metasploitable is intentionally, remotely exploitable, so it lives on an isolated internal network with no route to the host, the LAN, or the internet. That containment is a deliberate safety decision, and saying so unprompted signals maturity.

Why not host-only networking?
Host-only would have been ideal (isolated and sniffable from the host), but it needs VirtualBox's network kernel extension, which requires a macOS approval and reboot that wasn't available. The workaround, capturing the engagement on Kali with tcpdump and analyzing it on the host, mirrors real SOC practice: capture in the field, analyze at the workstation.

One detail worth knowing cold

The sensor sniffs without sudo because the user is in the macOS access_bpf group, which grants read access to the packet-capture devices. That is why the whole thing can run and be scripted without root.

07 ML anomaly detection

Catching what no rule anticipated

Signatures and heuristics only catch what you thought to describe. The ML detector (ml_anomaly.py) adds unsupervised coverage: it learns a baseline of normal traffic and flags statistical outliers, using an Isolation Forest from scikit-learn.

It builds one feature vector per source IP per time window, with eight features: packet count, distinct destination ports, distinct destination hosts, SYN count, SYN ratio, mean packet size, distinct flag combinations, and total bytes. Trained on a benign capture, it then scores new traffic; an outlier is an anomaly.

It works on real captures
Trained only on benign browsing, it independently flagged the attacker in traffic it had never seen: the 1001-port scan (huge port fan-out, 0.93 SYN ratio) and the SYN flood (10,238 packets, SYN ratio 1.0), with no signature involved. This is the concrete backing for "machine learning for security analytics."
08 Correlation & risk

From alerts to incidents

A raw alert stream is noise. An analyst wants "what happened." The correlation engine (correlate.py) folds alerts into attacker-centric incidents: it groups by host-pair (so the attacker's probes and the victim's responses land together), attributes the attacker from who initiated reconnaissance, maps each alert to a kill-chain stage, and computes a risk score from severity plus how far the attack progressed.

Run against the Metasploitable engagement, 28 scattered alerts fold into one incident: attacker 10.10.10.10, the full chain Reconnaissance → Exploitation → Actions on Objectives, risk score 130. That is the difference between a log and a story.

09 Notifications

Getting paged in real time

A notification sink fires on high-severity alerts through any of four channels, all from the standard library (no extra dependencies): a macOS desktop banner for local demos, ntfy for free push to your phone with no account, a Slack or Discord webhook, and Resend for email. Alerts are severity-gated and rate-limited per signature so one attack doesn't spam you. The ntfy path is verified end to end: a critical alert arrives on the phone with a title, priority, and a warning-light tag.

11 Interview Q&A

Questions you should be ready for

Open each one and answer it out loud before reading. These are the questions this project invites.

Q What's the difference between an IDS and an IPS?

An IDS detects and alerts; it's passive and sits out of band. An IPS prevents, sitting inline so it can drop or block malicious traffic. sentinel-ids is an IDS: it observes a copy of the traffic and raises alerts, which is why it can run without being in the packet path.

Q Signature-based vs anomaly-based detection, and which did you build?

Signature-based matches known-bad patterns: precise, low false positives, but blind to novel attacks. Anomaly-based flags deviations from normal: catches new threats but noisier. I built both. The heuristics and regex engine are signature/rule-based; the Isolation Forest is anomaly-based. Layering them is how real systems balance precision and coverage.

Q How do you detect a port scan when no single packet is malicious?

State over a sliding time window. I track distinct destination ports per source IP over a rolling window and alert when the count crosses a threshold, for example 15 distinct ports in 10 seconds. A cooldown then suppresses duplicates so one scan is one alert.

Q What is a NULL / FIN / XMAS scan and why can you detect it?

They're stealth scans that send TCP packets with unusual flag combinations: no flags (NULL), only FIN, or FIN+PSH+URG (XMAS). A compliant stack answers closed ports with RST and stays silent on open ones, which leaks port state. A real connection never sends these combinations, so their mere presence is the signature.

Q How does the ARP spoofing detector work?

It tracks the MAC address bound to each IP. When an IP suddenly maps to a new MAC, that's the fingerprint of ARP cache poisoning, the setup for a man-in-the-middle. In the lab this also fired benignly when the VM's MAC changed, which is a good example to raise: a true detection of the mechanism that a real deployment would tune with a host allowlist.

Q Walk me through the vsftpd 2.3.4 exploit.

vsftpd 2.3.4 shipped with a backdoor (CVE-2011-2523). If the FTP username ends in :), the daemon opens a root shell listening on port 6200. So you connect to FTP, send a username with the smiley, then connect to 6200 and you're root. No password, no memory corruption, just a malicious build.

Q How did you avoid false positives?

Thresholds tuned to real behavior, cooldowns to prevent alert storms, and a dedicated zero-false-positive test: normal repeated HTTPS traffic to one host must not trip the scan detectors. It's one of 20 tests in the suite.

Q What's MITRE ATT&CK and why tag alerts with it?

It's a knowledge base of real adversary tactics and techniques. Tagging each alert with its technique ID (a port scan is T1046, Network Service Discovery) lets defenders speak a common language, map coverage, and hand analysts context. It's expected vocabulary in a SOC.

Q Why put Metasploitable on an isolated network?

Because it's deliberately, remotely exploitable. Bridging it to a real network would expose an unpatched, rootable box to anything on that network. I put it on an internal-only VirtualBox network with no host, LAN, or internet route, so the only thing that can reach it is the Kali attacker.

Q What would you improve or do differently?

Honest answers land well: add TLS/encrypted-traffic analysis (payload signatures can't see into TLS), tune the ARP detector with a host allowlist, expand the ML feature set and validate on a larger benign baseline, and add IPS-style blocking as an option. I'd also fix the Metasploit runtime so exploitation can use modules alongside the manual work.

Q How would this scale to real network volume?

The Python/scapy path is fine for a lab but not line-rate. At scale you'd tap traffic with a proper capture layer (AF_PACKET, PF_RING, or a SPAN port), keep the sliding-window state bounded with periodic GC (which I already do), and for production reach for a purpose-built engine like Suricata or Zeek, feeding alerts into a SIEM. My JSONL output is already shaped for that ingest.

12 Run it yourself

The fastest paths to a working demo

The offline demo needs no VM and no root. It synthesizes one clean example of every attack, runs the IDS, and writes an HTML report.

cd ~/ids-lab
make setup      # venv + scapy, pyyaml, rich
make test       # 20 tests
make demo       # replay attacks -> logs/report.html

# correlate an alert log into incidents
sentinel-correlate -i logs/pentest_alerts.jsonl -o incidents.html

# train the ML detector on benign traffic, then score a capture
sentinel-ml train -b logs/benign_baseline.pcap
sentinel-ml score -r logs/wireshark_capture.pcapng

For a live run, start the sensor on the host and attack from Kali. The full step-by-step, including current IP discovery, is in docs/RUNBOOK.md. The pen-test writeup is docs/PENTEST_REPORT.html.
